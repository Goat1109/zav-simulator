# Frontier 의도하지 않은 되돌아감 진단

같은 500.54m 전체 복도 경로, 같은 `common.yaml`, Isaac Sim과 RViz를 켠 조건에서 재현했다. 복도 끝의 의도된 유턴과 그 이전 전진 중의 되돌아감을 분리해 실제 body 위치로 측정한다.

`log/frontier-20261118/backtracking/trial15-reproduce/`에서 첫 복도 끝 도달 전 최대 3.266m 되돌아감을 재현했다. Y 약 41.21m에서 38.04m까지 돌아갔다. 초기 경유점 자체는 복도 끝까지 Y가 증가하므로 bag의 의도된 왕복이 아니다.

이전 수정에서 도입한 이동 중 약 2초 간격의 전체 Path 재발행이 원인이다. 소비자는 새로운 경로가 오면 새 임무 경로로 받아 진행 상태와 preview를 초기화한다. 발행기의 진행·위치 정보 지연과 함께 이미 지난 경유점이 새 경로 앞에 붙어 역방향 목표가 생겼다. 이전 trial14에서도 sim58.81초의 새 Path 첫 Y가4.18m인데 실제 기체는 약11.6m까지 전진한 사례를 확인했다.

수정 내용:

- 비행 중 정합을 이유로 주기적으로 전체 Path를 다시 발행하던 처리를 제거했다. 현재는 이동 중 정합 결과를 강체 좌표 보정으로만 전달해 segment·누적 진행 상태를 보존한다. 새 Path를 전달하는 정체 복구는 실제 정지한 경우에만 수행한다.
- 위치·점군 수신 큐를 최신 1개로 제한하고 정합 전후 준비된 피드백을 처리한다. 실제 진행 계산 시각과 경로 revision이 맞는지 확인한다.
- 정체 복구 시 같은 순서의 직선 구간에서 실제 지나간 정점을 다시 포함하지 않는다. 아직 방문하지 않은 모서리와 복도 끝 유턴은 보존한다.
- 같은 경로의 주기적 재전송은 진행 상태를 보존한다. 실제로 바뀐 EPIC 상위 경로를 받는 인터페이스는 유지한다.

trial16은 freshness 처리만 수정한 중간 시험으로 첫 계단에서 접촉·FAULT가 발생해 실패했다. 위 주기적 경로 재발행 자체를 제거한 trial17에서 같은 첫 복도 끝까지 전진 중 최대 되돌아감 0m, 역행 구간 0건을 확인했다. 계단 쪽으로 돌아오는 정상 복도 왕복은 유지한다. 전체 층 완주 결과와 혼동하지 않는다.

기록: `trial15-reproduce/backtracking-audit.json`, `trial17-stable-path/backtracking-audit.json`과 각각의 `outbound-progress.png`. 전체 주행은 세 번째 복도 귀환 중 접촉 후 LIO safety landing latch로 중단됐고, 최상층 완주는 실패했다. penalty·속도·가속도·저크·지도 파라미터를 포함한 common YAML은 바이트 단위로 같다. 정합/정점 보존 회귀 7개, 임무 회귀 20개가 통과했다.


## 남아 있는 별도의 후퇴

trial17의 두 번째 복도 전진에서는 약 2.250m 후퇴가 남았다. sim135.26~136.71초에 실제 body Y가17.64m에서15.39m로 감소했다. 이 구간은 상위 Path revision10이 그대로였고, lookahead 목표 Y는22.2m 이상으로 계속 앞에 있었다. SUPER가 발행한 polynomial의 Y 속도는 sim135.5초에-1.22m/s,136초에-2.45m/s였다. 같은 시점에 GenerateExpTrajectory/backup 최적화 실패 로그가 반복됐다. 따라서 주기적 Path 초기화와 별도로 로컬 실행 궤적이 후퇴하는 문제가 남는다. 그 순간 실제 backup flag는 기록되지 않아 백업 진입 여부 자체를 확정하지는 않는다.

전체 구간별 결과는 `trial17-stable-path/all-corridor-backtracking.json`을 참고한다. 첫 복도 전진 역행0m, 복귀 역행최대0.20m; 두 번째 복도 전진2.25m, 복귀0.08m; 세 번째 복도 전진0.32m이다. 전체 문제가 해결됐다고 판정하지 않는다. 마지막 시험은 14/26구간 뒤 실패했으며, 동일500m 경로와 원래 common 파라미터를 유지했다.

## 윗층 도착 후 두 번 정지하는 이유

첫 층의 경우 경로 vertex9(윗층 도착)와 vertex12(복도 진입 코너)가 각각 `viewpoint_pause_indices`에 있다. 생성기가 stair arrival과 corridor junction을 모두 정지 관측점으로 넣었기 때문이다. 각 Path 끝에서 위치 오차0.15m 이내·속도0.3m/s 미만을 확인해 hold를 요청한 뒤, 발행기는 `viewpoint_wait_seconds=3.0`만큼 기다리고 다음 Path를 보낸다. 속도 조건이 잠시 깨지면 대기 카운터가 다시 시작돼 체감 정지 시간은 더 길 수 있다.

이 두 정지는 테스트 경로 발행기가 명시적으로 나눈 정지이며, 위의 주행 중 후퇴와 별개다. 대기 시간만0으로 바꿔도 각 Path 끝의 정지 조건은 남는다. 연속 통과로 바꾸려면 해당 지점을 같은 Path의 일반 경유점으로 합쳐야 한다. 위 원인 진단 시점에는 정지 지점 자체를 변경하지 않았다. 이후 사용자 요청으로 아래와 같이 변경했다.


이후 사용자 요청에 따라25개 중간 정지점을 모두 비우고 하나의 연속 Path로 변경했다. trial18에서 윗층 도착0.795m/s, 복도 코너0.442m/s의 실제 body 속도로 통과했고 중간 hold/3초 대기가 없음을 확인했다. [현재 경로 설정](frontier-all-floors.md)의 연속 모드 항목과 `continuous-waypoints/trial18-no-scripted-stops/continuous-audit.json`을 참고한다.


후속 원인 수정으로 같은 연속 500.54m 경로를 trial30·31에서 두 번 연속 무충돌 완주하고 최상층 LANDED를 확인했다. 센서/추정 시각·물리 자세·재계획 실행 수정과 전체 판정은 [전 구간 완주 기록](frontier-all-floors.md#전-구간-충돌-원인-수정-및-완주-검증)을 참고한다. 이전 trial17의 후퇴 수치는 수정 전 기록이다.
